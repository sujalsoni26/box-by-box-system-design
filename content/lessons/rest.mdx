An **API** is the contract between pieces of software: what you can ask, in what format, and what comes back.

**REST** models everything as a **resource** with a URL, and HTTP methods are the verbs:

| Action | Request |
| --- | --- |
| Get a user | `GET /users/42` |
| Create a post | `POST /posts` |
| Replace a profile | `PUT /users/42` |
| Edit part of a profile | `PATCH /users/42` |
| Delete a post | `DELETE /posts/7` |

- **URLs are nouns.** Avoid verb URLs like `/getUser`.
- **Stateless.** Every request carries its token and parameters, so any server behind the LB can answer. Data still lives in the database; the server just keeps no per-client session.

<Comparison>

<ComparisonItem title="Pros">

- JSON: readable and universal
- Simple; every language and browser speaks it
- GET responses are cacheable

</ComparisonItem>

<ComparisonItem title="Cons">

- Verbose text format
- **Under-fetching**: a screen may need several calls
- **Over-fetching**: an endpoint returns more than you need

</ComparisonItem>

</Comparison>

**GraphQL** addresses both fetching problems: the client asks for exactly the fields it needs in one request.

<DeepDive title="Go deeper: paginating big lists">

A feed can't return a million posts at once. **Offset pagination** (`?offset=40&limit=20`) is simple but slows down on deep pages and skips or repeats items when new posts arrive. **Cursor pagination** (`?after=post_9812&limit=20`) asks for "20 items after this one". It stays fast with an index and stable as the feed changes, which is why most social APIs use it.

</DeepDive>
